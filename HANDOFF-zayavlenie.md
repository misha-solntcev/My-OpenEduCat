## 26.11.2026 (1): партнёр приёмки — заявитель, не ученик

Ядро OpenEduCat в `enroll_student` после зачисления перезаписывало
`op.admission.partner_id` контактом **ученика**. Из-за этого вкладка
«Заявитель» показывала ребёнка (и onchange родительских данных, и
телефон заявителя искали не того человека).

- Перезапись снята: `partner_id` остаётся контактом заявителя
  (родителя), контакт ученика — в `student_id.partner_id`. Потребителей
  старого поведения в базе нет (счета/подписки идут от
  `op.student`/`op.parent`).
- В форме вкладки «Заявитель» поле подписано «Контакт заявителя».
- Старые приёмки (в проде и test4 по 133, из них с родителем 120)
  чинятся скриптом `scripts/rost_admission_applicant_fix.py`
  (DRY-RUN по умолчанию, запись — `ROST_APPLY=1`, бэкап old→new в CSV).
  На test4 прогнан, 120 записей исправлены; на проде — после
  подтверждения.

## LIN-13 (26.11.2026): телефоны — родителя и ребёнка, без «телефона семьи»

Модель телефонов (решение Миши):

- два разных номера — **телефон родителя** и **телефон ребёнка**;
  каждый живёт в Mobile своего контакта (`res.partner.mobile`) и
  правится там (в карточке родителя/ученика поле наследуется из
  контакта);
- понятия «телефон семьи» больше нет: поля `op.admission.phone`/
  `mobile` (подписи были «Телефон семьи»/«Мобильный семьи») в форме
  скрыты и кодом не читаются/не пишутся — это legacy-колонки;
- `op.student.mobile` больше НЕ своё поле модели: объявление убрано,
  значение наследуется из `partner_id` через `_inherits` (как
  `op.parent.mobile` — их related на контакт). Правка «Mobile» в
  карточке ученика пишет в контакт; колонка `op_student.mobile`
  осталась в БД как осиротевшая (значений на проде 1, на test4 1 —
  дубль контакта), чистится отдельным шагом;
- анкета: «Телефон» → Mobile контакта заявителя (+ Phone через
  нативный CRM-inverse `crm.lead.phone`), «Телефон ученика» →
  `child_phone` лида → при зачислении Mobile контакта ученика;
- приёмка: вкладка «Заявитель» — «Телефон заявителя»
  (`parent_phone`), compute/inverse: до зачисления контакт заявителя,
  после — контакт родителя из `op.parent` (ядро перезаписывает
  `partner_id` приёмки партнёром УЧЕНИКА, поэтому читать оттуда
  телефон после зачисления нельзя). Пишет в Mobile контакта;
- в контакт ученика родительский номер не попадает ни на одном шаге.

Существующие контакты (10 учеников с номерами родителей в test4/проде)
не трогали — школа разбирает их вручную.

## LIN-7 (26.11.2026): дособрана анкета родителя

Раньше анкета собирала только ФИО/дату/пол ребёнка, контакты и три
документа. Добавлено:

- **Данные ребёнка**: СНИЛС (обязателен, 11 цифр), ИНН (10/12 цифр),
  свой email и телефон — поля ручного ввода в анкете и на лиде
  (`child_snils`, `child_inn`, `child_email`, `child_phone`).
- **Паспортные данные заявителя** (текстом, для договора):
  дата рождения, серия и номер, кем выдан, дата выдачи, код
  подразделения, адрес регистрации и фактического проживания —
  поля `parent_*` на `crm.lead` (зеркало одноимённых полей приёмки).
- **Фото** ребёнка и заявителя — `Image`-поля лида (`child_photo`,
  `parent_photo`), превью в форме по токену
  `/zayavlenie/<token>/photo/child|parent`. Не вложения: при
  зачислении становятся аватарами ученика и контакта родителя.
- **Документы**: `birth_cert` (свидетельство о рождении) и
  `child_passport` (паспорт ребёнка) — нужен ОДИН из двух;
  `passport` — скан паспорта заявителя (переименован в «Паспорт
  заявителя (скан)», при зачислении уезжает в `op.parent`).
  Обязательны: СНИЛС, полис, паспорт заявителя, один документ
  ребёнка.
- **Раскладка**: подписи слева от полей (Bootstrap row +
  `col-form-label`), контейнер шире (`col-lg-11 col-xl-10`);
  на мобильном подписи снова над полями (`col-md-*`).

Поток данных: анкета → `crm.lead` → `sale.order.action_open_admission`
(копирует `parent_*`, `child_snils/inn/phone`, фото в `image`
приёмки) → `enroll_student` → `op.student.snils/inn/mobile/avatar` и
`op.parent` (паспорт) + аватар контакта.

## Итог (20.11.2026)

Реализовано заявление о приёме по персональной ссылке — **не** survey
и **не** форма на `op.admission`, как в исходном плане ниже.

- Модель-носитель: **`crm.lead`** — лид существует с начала воронки,
  заказ и приёмка ссылаются на него (`sale_order_id.opportunity_id`),
  файлы не дублируются.
- Доступ: **персональная ссылка** `/zayavlenie/<token>` по токену,
  срок 7 дней от выдачи; публичной страницы в меню сайта нет.
- UI анкеты — **на подтверждённом заказе** (state='sale'): related-поля
  статуса через `opportunity_id`, кнопки «Отправить анкету» /
  «Открыть анкету» / «Новая ссылка», цветные alert-полосы
  (info/success/warning) под шапкой. На лиде и приёмке анкеты-UI нет.
- Обязательные документы: **СНИЛС**, **медстраховой полис**; опционально
  «Другие документы» (несколько) и комментарий. PDF/JPG/PNG/HEIC,
  до 10 МБ на файл, 50 МБ на форму.
- Три согласия (перс. данные, психсопровождение, условия договора).
- Код: `controllers/main.py` (GET форма / POST submit / GET doc по
  токену) + `views/website_templates.xml` (рукописная разметка **без**
  класса `s_website_form` — он вешает JS-виджет сниппета) в
  `rost_school_billing`; depends +`website`, +`sale_crm`.
- Вложения — `ir.attachment` с `rost_doc_type` (snils/policy/
  birth_cert/passport/consent/other); скачивание только своим роутом
  по токену (`/web/content` анониму отвечает 403, все обращения к
  вложениям в публичном контроллере — через sudo).
- При зачислении документы **переезжают** (смена res_model/res_id):
  snils/policy/birth_cert/other → `op.student`, passport/consent →
  `op.parent` (`op.student.rost_adopt_zayavlenie_documents` + override
  `enroll_student` в billing; заявитель сохраняется ДО super()).
- «Созданной» ссылки нет: токен выдаётся кнопкой «Отправить анкету»
  (письмо родителю через composer), «Новая ссылка» перевыпускает
  токен; без ссылки кнопка «Открыть анкету» даёт notification.

Проверено на test4 20.11.2026: HTTP E2E анонимной сессией (32 проверки:
валидация, файлы, замена СНИЛС, 404 на чужие вложения, просрочка),
перенос при зачислении в savepoint, кнопочные методы, вёрстка в
браузере. Коммиты `45a2499`, `81e22bc`.
